2. **NIT — `MaxRequestNodes` (16,384) lets inner replies exceed `MaxReplyBytes` (1 MiB) by 8× and gives 256× decoder amplification** (`internal/merkle/wire.go:17-18, 227-230`, `internal/merkle/diff.go:79-88`)
   - **What is wrong:** `Tree.Answer` caps `msgLeaves` replies at `MaxReplyBytes` (1 MiB), but does not cap `msgInner` replies (`diff.go:79-88`). Because `MaxRequestNodes = 16384` and each full inner node encodes to `2 + 16*32 = 514` bytes, a valid 32 KiB inner request at level 3–4 (or a caller using `Limits{Frontier: 4096}`, which `Limits.frontier()` allows up to `MaxRequestNodes`) causes `Answer` to allocate and emit up to `5 + 16384*514 ≈ 8.03 MiB` — 8× above `MaxReplyBytes` (and a hostile 32 KiB `msgInner` reply with `n = 16384` zero bitmaps causes `decodeResponse` to allocate `make([][16]Hash, 16384) = 8 MiB` before `Session.apply` checks `len(r.inner) != len(s.sent)`). On a real TCP runtime with a frame limit sized near `MaxReplyBytes`, inner replies with `Frontier > 2040` will fail with `env.ErrTooLarge`.
   - **Reproduction:** Construct a `Tree` at depth 4 with > 4,096 populated level-3 nodes and run `Compare(empty, full, Limits{Frontier: 4096})` (or pass a `decodeRequest`-valid 16,384-path level-3 request to `Answer`): the returned `msgInner` reply exceeds `MaxReplyBytes` (up to ~8.03 MiB). Feed `[0x02, 0x00, 0x80, 0x80, 0x01]` + `32768` zero bytes to `decodeResponse`: it allocates an 8 MiB slice from a 32 KiB input.
   - **Smallest fix:** Lower `MaxRequestNodes` to `2040` (or `1024`, matching `DefaultFrontier`), since `5 + 2040*514 = 1,048,565 <= MaxReplyBytes` (1 MiB). This bounds both `Answer`'s `msgInner` output and `decodeResponse`'s inner allocation to `<= 1 MiB` without changing `DefaultFrontier` (1,024). (Note: a single `MaxLeafEntries = 4096` leaf with 1,024-byte keys can still produce ~4.13 MiB so the first leaf always makes progress; keep that documented for Chunk 6's TCP `MaxMessage`.)

7. **NOTE — Round-trip count is `Depth + 1` (number of tree levels) vs PLAN's "round trips ≤ depth"** (`internal/merkle/diff.go`, `agent_work/03-merkle/build-notes.md:63-65`)
   - **Observation:** Confirmed as flagged in `build-notes.md:63-65`. With `Depth` as the leaf level (`16^Depth` leaves, `Depth + 1` levels total from level 0 root through level `Depth` leaves), a non-empty diff requires `Depth + 1` round trips (root check + `Depth - 1` inner levels + 1 leaf-entry fetch), and 1 round trip when roots match. This is inherent to a fixed-depth trie without over-fetching all 16 sibling leaves at level `Depth - 1`. The property bound `<= Depth + 1` and cost table are accurate; the prose/book stage should state `Depth + 1` round trips (one per tree level, root through leaves) and note leaf-batching beyond `MaxReplyBytes`.
