## New Findings

### 1. MAJOR — `recordOrphans` overwrites `~orphan/<version>/<node>` across ticks, breaking lost-object detection for multi-stripe objects
- **File & lines:** `internal/node/inventory.go:267-293` (`recordOrphans`), `internal/node/inventory.go:295-329` (`noteOrphan`), `internal/node/inventory.go:331-382` (`lostByOrphans`, `declareLost`).
- **What is wrong:** `recordOrphans` writes the `(stripe, index)` pairs collected during the current maintenance tick to key `~orphan/<version>/<node>` via unconditional `n.occ.SetScalar(k, w.b)` without reading or merging previously recorded `(stripe, index)` pairs for that `(version, node)`. Any multi-stripe object (`size > StripeSize`, e.g. > 1 MiB in production or > 4 KiB in DSTs; note `storage.DefaultWindow = 4` launches stripes 0..3 before stripe 4, and retries or RTTs easily cross the 500 ms `MaintainPeriod`) commonly has shards of different stripes arrive on the same holder `H` in different maintenance ticks. `OrphanGrace` then expires for stripe 0 in tick `T` (writing `[(0, i)]` and deleting the shard) and for stripe 1 (or 4) in tick `T+1` (overwriting `~orphan/<v>/<H>` with `[(1, j)]`, erasing `(0, i)`). When the isolated writer rejoins, `noteOrphan` under-counts stripe 0's deleted shards; `lostByOrphans` returns `false`, `declareLost` never tombstones the object or writes `~lost/<v>`, and every `GetObject` returns permanent `storage.ErrUnavailable` on a key metadata calls live. This directly breaks the repair's stated residual-case guarantee (`build-notes.md:516-518`: "declared lost with a record, never left live and unreadable"), which `TestAWriteWhoseShardsWereCollectedAsOrphansIsRecordedLost` missed because it writes only a 3,000-byte single-stripe object (`gc_test.go:152`, `StripeSize = 4096`).
- **Concrete reproduction:**
  1. Cluster of 7 nodes in `r0` (`k=4, m=2`, `StripeSize=4096`), writer `n6`, 2-stripe object (`5000 B`, version `V`) placed so stripe 0 is on `{n0,n1,n2,n3,n4,n6}` and stripe 1 is on `{n0,n1,n3,n4,n5,n6}` (`n2` is not on stripe 1).
  2. Shard `(1, ...)` to `n0` arrives one maintenance tick (≥ 500 ms) after shard `(0, ...)` (e.g., delayed link or > 4 stripes with `DefaultWindow=4`); `n6` commits and is isolated for `> OrphanGrace`, while `n0, n1, n2` do not hold the manifest.
  3. At `T + OrphanGrace`, `n0, n1, n2` collect stripe 0's shards (`3 > m=2` shards deleted -> stripe 0 is permanently unrecoverable) and write `~orphan/<V>/n0`, `n1`, `n2`.
  4. At `T + 500ms + OrphanGrace`, `n0` collects stripe 1's shard and overwrites `~orphan/<V>/n0` with only `[(1, ...)]`, erasing `(0, ...)`.
  5. `n6` rejoins: `n.orphaned[V]` records only 2 orphans for stripe 0 (`n1, n2`) and 2 for stripe 1 (`n0, n1`) — both `<= m=2`. `lostByOrphans` returns `false`, `V` remains live with zero `~lost/` record, rebuilds fail indefinitely, and `GetObject` returns `storage.ErrUnavailable` forever.
- **Smallest fix:** Key orphan records per shard (or per stripe), e.g. `~orphan/<version>/<node>/<stripe>/<index>`, or read existing `(stripe, index)` entries from `rd.Get(k)` in `recordOrphans` and write the sorted union before collecting. Extend `TestAWriteWhoseShardsWereCollectedAsOrphansIsRecordedLost` (or add a sibling test) with a multi-stripe object whose shards arrive across maintenance ticks.

### 2. MAJOR — `realNet.Request` invokes its callback twice on `timeout <= 0` and on oversized self-requests
- **File & lines:** `internal/noderuntime/runtime.go:563-595` (`realNet.Request`).
- **What is wrong:** `realNet.Request` allocates `rt.pending[id] = true` and arms `tm = rt.afterFunc(timeout, func() { complete(nil, ...ErrTimeout) })` on lines 567–581 *before* checking `if timeout <= 0` (line 582) and `if to == rt.cfg.ID && len(req) > node.MaxFrame` (line 589). Both error branches then schedule `rt.afterFunc(0, func() { cb(...) })` directly instead of calling `complete(...)`, leaving `tm` armed and `rt.pending[id]` set. As a result, `cb` is invoked **twice** on both paths — violating `internal/env/env.go:67-71` ("invokes cb once"):
  - On `timeout <= 0`: `tm` fires immediately (`max(timeout, 0) == 0`) calling `cb(nil, ErrTimeout)` *and* the second timer calls `cb(nil, ErrInvalidArgument)`.
  - On self-request `len(req) > node.MaxFrame`: the 0-delay timer calls `cb(nil, ErrTooLarge)` *and* when `timeout` elapses, `tm` fires calling `cb(nil, ErrTimeout)`.
  Neither branch was tested when added in commit `2f8984c` for REVIEW-1 Finding 11. (Note: `Node` itself currently validates positive timeouts and avoids self-requests via `gossipView.Peers()`, so this is latent in `objnode` today but broken at the `env.Transport` layer.)
- **Concrete reproduction:** In a `synctest` bubble on `realNet{rt: rt}`, call `net.Request("solo", []byte{1}, 0, cb)` (or `net.Request("solo", make([]byte, MaxFrame+1), 10*time.Millisecond, cb)`), advance virtual time by `20ms`, and count invocations of `cb`: `cb` runs twice instead of once.
- **Smallest fix:** Move `if timeout <= 0` before `rt.nextID++`/`rt.pending[id]`/`tm = ...` (or call `complete` in both branches, after moving `tm` below `timeout <= 0` so `timeout <= 0` cannot race `tm`), and add a unit test in `internal/noderuntime/runtime_more_test.go` asserting `cb` is called exactly once with `env.ErrInvalidArgument` / `env.ErrTooLarge`.

### 3. NIT — `migrator.Flip` permanently fails and strands a bucket if a coordinator crashes between writing `~flip` and `SetRoute` during a concurrent migration

## Specific Re-Review Questions (1–5)

### 1. Breaking Finding 1's new rule
- **Live-peer pre-flip writes & writes racing agreement:** Sound. Once a peer returns `views[p]` with `route == m.To` and `owner == id|m.To`, `bs.writable()` is false (`route != ~live`), and any in-flight `PutObject` started before `route == m.To` re-checks `bs.writable() && bs.route == region` synchronously in `commitPut` (`objects.go:243`) before committing, marking its unwritten version dead if the bucket moved. Thus `Pointer`'s `agree()` guarantees the coordinator holds every manifest any live peer committed before stopping writes. If a new peer joins while `agree()` RPCs are in flight, `n.viewChanged` resets so `purge`'s own `ViewSettled()` check (`migrate.go:478`) refuses to purge until the view settles and `Retire` retries `agree()` including the new peer.
- **Coordinator restart between agreement and retire (or mid-`Retire`):** Sound. `Copy` skips live objects whose version is already in this saga's `~cv/<saga>/*` intents (`migrate.go:289-292`), and `Root(To)` unions live intent versions with staged entries (`migrate.go:375-388`), so a retry after partial swaps neither re-copies swapped objects nor fails `Root` verification. A crash between `dropIntents` (`migrate.go:785`) and `setScalar(~retired)` (`migrate.go:789`) safely re-copies live target objects into the target region without data loss.
- **Two migrations (duelling or sequential):** Sound for data safety. Per-saga `~reg/<saga>` keys commute; `~flip` determines a single winner even on same-target duels; if `route` lags `~flip`, the winner re-writes `SetRoute` and retries `Pointer` (`migrate.go:683-689`), while the loser sees a foreign `owner`, discards only its own `~cv/<saga>/*` intents, and deregisters so the winner can `Seal`. Only the narrow crash-between-two-writes window in `Flip` (New Finding 3) can strand `route != ~live` (no data loss). Sequential migrations cleanly copy and purge strays left in the old region by an earlier returning peer.
- **Not-live peer returning later (< `OrphanGrace`):** Sound. Its pre-flip version has no `~gc/` marker, so `Retire`'s explicit dead-version list omits it and its shards stay intact in `m.From`. On return, a new key stays live and readable from `m.From` (moved on next migration); an overwrite resolves under LWW with whichever version wins keeping its shards intact.
- **Stated residual (peer away > `OrphanGrace`):** Stated plainly in `build-notes.md:516-518, 541-549`, and tested for a single-stripe object by `TestAWriteWhoseShardsWereCollectedAsOrphansIsRecordedLost`. **However, the code does not uphold it for multi-stripe objects:** `recordOrphans` overwrites `~orphan/<version>/<node>` across maintenance ticks (New Finding 1), allowing a multi-stripe object whose stripe lost `> m` shards as orphans to remain live in metadata and permanently `ErrUnavailable`.
